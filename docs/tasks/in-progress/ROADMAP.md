### 0.1 `app/services/ai.py` — єдина точка входу до LLM

Уся робота з моделями йде тільки через цей модуль. Мета — аудитованість
(жоден особистий документ не потрапляє до зовнішньої моделі) та контроль токенів.

Архітектура — **бекенд-агностична, маршрутизація за типом задачі**:

| Задача | Пріоритет | Реалізація |
|---|---|---|
| Класифікація категорій товарів | локально → хмара | Локально: **Qwen2.5-3B-Instruct** Q4 через Ollama (найкраща кирилиця + JSON у класі 2-4B; Llama-3.2-3B **не** підходить — нема UA/RU). Цільове залізо — Orange Pi 5 Plus (RK3588, 16 GB, CPU). Запуск — `./ollama-docker.sh native` (host-install Ollama ~1.5 GB + тюнінг systemd; варіант `up` тягне контейнер `ollama/ollama` ~4.5 GB з CUDA/ROCm — зайве на CPU). Фолбек — дешева хмарна модель провайдера (Haiku / gpt-4o-mini / gemini-flash). |
| Нормалізація фрази списку → пошуковий запит під магазин | локально → хмара | Те саме; результат кешується назавжди. |
| OCR чека (vision) | хмара | Vision-модель обраного провайдера (Sonnet / gpt-4o / gemini-pro …). На міні-ПК якісна VLM не запуститься. Локальна VLM — можливий експеримент пізніше. |

**Конфіг — не через `.env`, а на окремій сторінці налаштувань у застосунку**
(див. розділ 0.2). Зберігається в `app_settings`, ключ `ai_config`:

```jsonc
{
  "local":  { "enabled": true,  "url": "http://localhost:11434",
              "model": "qwen2.5:3b-instruct", "num_ctx": 8192 },
  "cloud":  { "enabled": true,
              "provider": "anthropic",             // anthropic|openai|google|xai|deepseek|mistral
              "model_text": "claude-haiku-4-5",    // дешева модель для classify/normalize
              "model_vision": "claude-sonnet-5",   // vision-модель для OCR
              "anthropic_workspace_id": null },    // лише для identity-linked/admin ключів Anthropic
  "routing": {
    "classify":  ["local", "cloud"],   // порядок спроб
    "normalize": ["local", "cloud"],
    "ocr":       ["cloud"]
  },
  "monthly_token_budget": 2000000        // м'який ліміт, при перевищенні — тільки local
}
```

**Хмарний провайдер вибирається** зі списку: Anthropic Claude, OpenAI (ChatGPT),
Google Gemini, xAI Grok, DeepSeek, Mistral. Anthropic іде через власний SDK,
решта — через спільний OpenAI-сумісний HTTP-шлях (`/chat/completions`,
`/models`); Gemini — через свій OpenAI-сумісний ендпоінт. Vision (OCR) працює
для тих моделей провайдера, що це підтримують.

API-ключі — **по одному на провайдера** (перемикання не стирає інші), кожен
**зашифрований** через `core/security` (Fernet), як `Credential`-токени — не у
відкритому JSON. У формі — маскований (`••••1234`). `.env` лишається тільки для
`RS_SECRET_KEY` (Fernet-ключ) — єдиний секрет рівня інфраструктури.

Списки моделей для тексту/vision тягнуться з `/models` **обраного провайдера**
(`GET /api/settings/ai/models`, кнопка «Оновити список моделей» на сторінці).
Ендпоінт **самолікує** збережений конфіг: якщо модель зникла з відповіді
провайдера (застаріла → 404), її замінює `_pick_default_model` (дешевий
загальний чат: flash/mini/haiku…, не reasoning/tts/image/embedding) і зберігає —
щоб фоновий тик категоризації не сипав помилками. Плюс `normalize_cloud_models`
(`load_config`/`save_config`) підмінює модель, якщо в ній префікс іншого
провайдера. `_openai_call` прокидає текст помилки провайдера, а не голе «404».

М'яка деградація:
- нема жодного бекенда для текстової задачі → товар лишається без категорії
  (не помилка, повторимо пізніше);
- нема хмарного бекенда для OCR → конвеєр віддає найкращу чернетку з
  `scan_job.status = needs_review`, а не падає.

Публічний інтерфейс (реалізовано):

```python
async def classify_products(db, names: list[str], taxonomy: list[str]) -> dict[str, CategoryGuess]: ...
async def normalize_query(db, phrase: str, store_code: str) -> str: ...
async def ocr_receipt(db, image: bytes, media_type="image/jpeg") -> dict | None: ...
```

`ocr_receipt` повертає сирий dict (мапінг на `NormalizedReceipt` — у
`scanner/pipeline.py::_receipt_from_ai`). Усередині: батчинг, JSON-контракт,
кешування — на боці викликачів (`product_category` / `product_alias`).

**Облік і журнал** (`ai_usage` + `ai_log` у `app_settings`): `_run` — єдина точка
метрики й логування, міряє кожну спробу (backend, модель, токени in/out для
хмари **та** local з `prompt_eval_count`/`eval_count` Ollama, тривалість, ok/помилка).
`ai_log` — кільцевий буфер останніх 60 подій: кожен виклик несе `prompt` (що
надіслали — напр. «6 назв: куряча гомілка, …») і `response` (сира відповідь моделі
або текст помилки, напр. `429 You exceeded your current quota`) + підсумок батчу
категоризації. `GET /api/settings/ai/log`; на сторінці налаштувань — таблиця
«Журнал AI» з розкривними рядками (prompt / response), токени local у блоці
«Використання AI».
Класифікатор: `category_id_for_path` тепер матчить шлях **нестрого** (регістр,
`/ > \ |` як роздільники) — модель майже ніколи не повертає шлях байт-у-байт,
через що раніше «токени витрачено, категорій нема».

**Ручна обробка (без API-ключа).** `GET /api/categories/manual-prompt?limit=N`
віддає готовий промт (система + список назв + повне дерево) — користувач вставляє
його в будь-який чат-бот і повертає JSON у `POST /api/categories/manual-apply`.
Розбір толерантний (```-огорожа, рядок-значення, `path`/`category`/`category_path`),
далі — той самий `categorize.apply_guesses`, що й автопрохід (кеш у
`product_category`, застосування до позицій, ручні `source=user` недоторкані,
підсумковий запис у `ai_log`). UI — секція «Ручна обробка» на сторінці
«Категорії»: генерація/копіювання/завантаження промту, поле для відповіді.
Той самий підхід згодом можна дати для `normalize` / OCR.

### 0.2 Сторінка налаштувань (`SettingsView`)

Уся конфігурація етапу — наочно в UI, не в `.env`. Джерело правди — таблиця
`app_settings` (уже є, див. модель `AppSetting` та `api/settings.py`). Нова
сторінка з розділами:

| Розділ | Ключ `app_settings` | Що редагується |
|---|---|---|
| **AI / моделі** | `ai_config` | вмик/вимк local та cloud, URL і модель Ollama (випадайка з `/api/tags`), **вибір хмарного провайдера** + його моделі для тексту й vision (випадайки з `/models` провайдера), порядок маршрутизації по задачах, місячний бюджет токенів. Кнопка «Перевірити зʼєднання». Ключі провайдерів — окремі поля (по одному на провайдера, зашифровані, masковані) з кнопкою «Тест» (валідує ключ до збереження). |
| **Використання AI** | `ai_usage` (лише читання) | лічильник токенів за місяць, скільки запитів пішло local vs cloud, залишок бюджету. |
| **Google Drive** | `drive_config` | статус OAuth, вибір кореневої папки та папки «Необроблені» (обхід дерева Drive). |
| **Інбокс / роутинг** | `inbox_config` | поріг співвідношення сторін «чек vs документ», максимальний розмір файлу. |
| **Категорії** | — | посилання на керування деревом категорій (крок 1). |

Реалізовані ендпоінти (`api/settings.py`):
- `GET/PUT /api/settings/ai` — конфіг (`ai_config`, Pydantic-валідація);
- `PUT /api/settings/ai/cloud-key` — `{provider, api_key}`, шифрується per-provider,
  у відповідь лише масковки `{provider: "••••1234"}`, ключ назад ніколи не віддається;
- `POST /api/settings/ai/check` — перевірка local (`/api/tags`) і cloud (ping);
- `POST /api/settings/ai/test-key` — `{provider, api_key?, model?, anthropic_workspace_id?}` — кнопка «Тест»
  біля поля ключа: валідує щойно введений ключ (або збережений) без запису в БД і
  без обліку токенів;
- `GET /api/settings/ai/models` — списки моделей для випадайок: local з Ollama
  `/api/tags`, cloud з `/models` обраного провайдера (Anthropic — через SDK), або
  статичний fallback без ключа;
- `GET` повертає й `ai_usage` (лише читання).
Загальні `GET/PUT /api/settings/{key}` лишились для решти ключів, але явно
відмовляють для `ai_config`/`ai_cloud_key`/`ai_usage` (щоб не затерти секрет).

`inbox_config` — розділ «Інбокс · роутинг» на `SettingsView` (пороги форми й
кольору, ліміт розміру). `drive_config` — розділ «Google Drive» показує статус;
кнопка OAuth-підключення ще попереду. API — `/api/inbox/config`,
`/api/inbox/drive-config`.
Секція «Категорії» — керується на окремій сторінці `CategoriesView` (крок 1).

Патерн уже закладено в пам'ятці проєкту: `app_settings` — місце для
користувацької конфігурації, що не варта власної таблиці.

## Крок 1. Таксономія категорій + AI-класифікатор ✅ зроблено (2026-08-29)

**Мета:** вкладені категорії товарів, автоматичне розкладання позицій, основа для
дашбордів, пошуку та підбору магазину.

Реалізовано: моделі `Category` / `ProductCategory` + `ReceiptItem.category_id`
(стара `category` → `category_raw`), `Store.network_type`; Alembic-ревізія
`b2c1d4e5f6a7`; сид дерева категорій (`app/seed.py::seed_categories`,
«Класифікація покупок та витрат» — 20 коренів / ~270 вузлів до 3 рівнів;
переглянуто й перебудовано 2026-08-30, ревізія `e7a2c4b91f30` очищає старе
дерево + усі класифікації на наявних БД); `app/services/text.py` (`normalize_name`, `slugify`) та
`app/services/categorize.py` (детермінований `apply_known_categories` на кожному
збереженні чека + фонова `run_classification_batch` через `ai.classify_products`,
липкий `source=user`); `api/categories.py` (CRUD із каскадним `path`,
`POST /backfill?force=`), `GET /api/dashboard/by-category`; фоновий тик кожні
10 хв у `scheduler.py`; скрипт `scripts/backfill_categories.py [--force]`.
Фронтенд: `CategoriesView` (кнопки «Розібрати "Без категорії"» та
«Переразподілити все»), вибір категорії в позиції чека, блок «Витрати за
категоріями» з drill-down (нульові гілки сховані).
Тести — `tests/test_text.py`, `test_categories.py`, `test_categorize.py`.
Разовий бекфіл історії — запустити після ввімкнення AI-бекенда на сторінці
налаштувань. Стандартний режим бере лише чергу «Без категорії»; `force` спершу
скидає всі AI-аліаси (ручні `source=user` лишаються) і переразбиває всю історію.

### Дані
- Нова таблиця `category`:
  `id, parent_id (nullable, FK self), name, slug, path` (матеріалізований шлях,
  напр. `продукти/овочі`), `sort_order`.
- Сид стартової таксономії (`app/seed.py::CATEGORY_TREE`, «Класифікація покупок
  та витрат»): 20 коренів — Продукти, Напої, Солодощі та снеки, Побутова хімія…,
  Гігієна та косметика, Дім та кухня, Сад та ділянка, Будівництво та ремонт,
  Інженерні системи будинку, Авто, Техніка та електроніка, Розумний дім та
  безпека, Здоров'я та аптека, Одяг та взуття, Діти, Освіта, Дозвілля, Подорожі,
  Послуги та платежі, Інше.
- `ReceiptItem`: додати `category_id` (FK, nullable). Стару строкову `category`
  лишити як `category_raw` (сире значення від магазину).
- Нова таблиця `product_category` — аліас-кеш:
  `normalized_name (PK), category_id, source (ai|user|store), confidence, updated_at`.
  Один рядок на унікальну назву товару за весь час.

### Логіка
- `normalize_name(raw)` — нижній регістр, стиснення пробілів, викидання ваги/обсягу
  в кінці (`0,9 л`, `1 кг`), артикулів. Спільна утиліта, знадобиться і кроку 2.
- При збереженні чека (колектор + ручний імпорт + OCR): для кожної позиції
  дивимось `product_category` за `normalized_name`. Є — проставляємо `category_id`.
  Нема — кладемо в чергу «нових назв».
- Фонова задача (scheduler): бере накопичені нові назви, батчить по ~50,
  `categorize.classify_hierarchical()`, пише результат у `product_category`,
  потім проставляє `category_id` всім позиціям із цими назвами.
- **Дворівнева класифікація** (щоб не слати в модель усе дерево на кожен запит):
  1. прохід 1 — розкладаємо кожну назву по **кореневих** категоріях (у промпті
     лише ~15 коренів + назви товарів);
  2. прохід 2 — для кожного кореневого «кошика» окремим запитом розкладаємо його
     товари лише по його гілці. Якщо підкатегорія неясна — лишаємо кореневу.
  Однорівневе дерево → один плоский виклик, як було.
- Магазини не класифікуємо окремо — достатньо довідника `store_code → тип мережі`
  (супермаркет / АЗС / техніка …) у сіді `Store`.

### API
- `GET /api/categories` — дерево.
- `POST /api/categories`, `PATCH /api/categories/{id}`, `DELETE` (з переносом дітей).
- `PATCH /api/receipts/{id}/items/{item_id}` — вже є; додати підтримку `category_id`.
  Ручна зміна категорії позиції → оновлює `product_category` з `source=user`
  (липке, більше не перезаписується AI).

### Frontend

### Логіка роутингу

Два сигнали, обидва пороги — в `inbox_config` на сторінці налаштувань (їх
підбираємо на реальних сканах):

1. **Форма.** `receipt_ratio` — поріг h/w (зараз default 2.0, `aspect.py`).
   Орієнтир: паперовий чек вужчий за ~100 мм; звичайний документ близький до
   сторінки A4/A5. **Виняток — картки-документи:** посвідчення водія, ID-картка
   мають ширину як у чека, але це документи і в чеки потрапляти **не повинні** —
   тому саме форми недостатньо, потрібен другий сигнал.
2. **Кольоровість (новий маркер).** Чек — термодрук: майже монохромний, низька
   насиченість, мало «значущих» кольорів. Документ (права, паспорт, договір із
   печаткою/кольоровим бланком) — кольоровий. Рахуємо метрику: частку не-сірих
   пікселів / середню насиченість / кількість кольорів після квантування
   (`inbox_config.color_*`).

**Правило:**
- майже монохромне зображення → **чек**, незалежно від форми (найсильніший
  сигнал — сірий термочек так виглядає завжди);
- кольорове + форма сторінки або картки → **особистий документ**;
- інакше — за формою.

Чек → конвеєр розпізнавання нижче → `NormalizedReceipt` → той самий шлях
дедуплікації, що й в адаптерів (`store_code="scanner"`). Повна невдача →
`needs_manual_input`. Документ → гілка `services/inbox.py`, яка **не імпортує
`ai.py`** (є тест).

> Стан (2026-08-30): реалізовано. `aspect.color_stats` рахує середню насиченість
> + частку не-сірих пікселів; `aspect.route(shape, color, cfg)` застосовує
> правило вище; `api/inbox.py::upload` викликає його. Пороги — в `InboxConfig`,
> редагуються на `SettingsView`. Кольоровий сигнал best-effort: якщо метрику не
> порахувати, рішення падає назад на форму.

### Розпізнавання чеків: шаблони перш за все (AI — останній засіб)

Мета — щоб AI спрацьовував лише на кількох відсотках чеків. Конвеєр із раннім
виходом: як тільки етап дав результат, що **сходиться** (див. звірку нижче) —
зупиняємось, наступні етапи не виконуються.

1. **Фіскальний QR → кабінет ДПС (пріоритетний шлях).** Українські чеки ПРРО/РРО
   несуть QR з посиланням на `cabinet.tax.gov.ua/...check` з параметрами `fn`
   (фіскальний номер ПРРО), `id`/`date`/`time`/`sum`. Декодуємо QR з фото
   (OpenCV, `scanner/fiscal_qr.py`). Далі:
   - **основне** — тягнемо структурований чек із `cabinet.tax.gov.ua` за `fn+id`
     (`scanner/tax_cabinet.py`, best-effort; вмик/налаштування —
     `inbox_config` / прапорець `enable_tax_cabinet`). Якщо цей сервіс покриє
     чеки повністю — шаблони (крок 2 нижче) взагалі не знадобляться;
   - **мінімум** (кабінет недоступний) — уже маємо дату, суму, фіскальний номер:
     закриваємо чек без позицій або лишаємо `needs_review`.
   - **0 звернень до AI** на обох гілках.
2. **Шаблон мережі (додаємо пізніше, лише якщо кабінет ДПС не покриває).**
   Визначаємо мережу за шапкою чека (назва, **ЄДРПОУ/ІПН**, адреса) — звірка з
   довідником. Парсер макета: якірні регекси на поля (`СУМА`, `ПДВ`, `Знижка`,
   `Бонус`, `Каса`/`Касир`) + правило рядка позиції. **Шаблони — це дані, не код:**
   `backend/app/scanner/templates/*.yaml` (каркас матчера/парсера вже є в
   `scanner/templates.py`); додати мережу = додати файл. Форма результату —
   `NormalizedReceipt`.
3. **Загальний структурний парсер.** Для невідомих макетів: OCR-текст +
   bounding-box слів (локально — Tesseract `ukr+eng` або PaddleOCR, **без AI**) →
   евристики: знайти блок підсумків, колонку цін, рядки-позиції за патерном
   «текст … число». Best-effort чернетка з оцінкою впевненості.
4. **AI (vision) — тільки якщо** QR не зчитався, жоден шаблон не підійшов і
   загальний парсер дав низьку впевненість (див. звірку). Через `ai.ocr_receipt()`.
   Бонус: коли AI розібрав мережу, для якої шаблону ще нема — логуємо розкладку в
   `scan_sample`, щоб згодом дописати шаблон (крок 2) і більше AI на неї не
   витрачати.

**Звірка (де беремо впевненість):** `Σ(позиція.сума) − знижки ± похибка_округлення
== чек.разом`. Сходиться → приймаємо без AI. Не сходиться / позицій підозріло
мало / багато «сміттєвих» символів → ескалація на наступний етап.

**OCR-рушій — Tesseract `ukr`** (рішення прийнято; `scanner/ocr.py` — обгортка з
мʼякою деградацією `OcrUnavailable`, коли бінарник не встановлено). Системна
залежність образу: `tesseract-ocr` + `tesseract-ocr-ukr` у Dockerfile.

**Сутності** (`app/models/scanner.py`, Alembic `c3e5a1b2d4f6`) — вже створені:
- `scan_job` — журнал і черга ручного розбору; поле `method`
  (`qr|tax_cabinet|template:<code>|generic|ai|none`) дає статистику частки чеків,
  що дійшли до AI;
- `scan_sample` — сирі OCR-розкладки для авторства майбутніх шаблонів;
- `inbox_document` — див. «Документи» нижче.
- Довідник мереж `edrpou → мережа` — `app/scanner/networks.py` (окрема таблиця-
  довідник, не сід `Store`: містить і мережі без адаптера — аптеки, локальні
  магазини). `pipeline` проставляє назву/тип мережі на чеки, що дійшли лише до
  QR / generic / AI. Коди — best-effort, звіряти на реальних сканах.

**Готово, коли** чек із читабельним фіскальним QR розноситься без жодного
звернення до AI; частка чеків, що дійшли до AI, видна в статистиці
(`scan_job.method`).

### Реалізація
- `backend/app/mcp_server.py` — `FastMCP` (з `mcp==1.29.0`, без нової залежності),
  транспорт Streamable HTTP, `stateless_http=True`, `json_response=True`.
- Змонтовано як sub-app до FastAPI на `/mcp` (`app/main.py`), після всіх
  `/api`-роутерів; лайфспан session-manager'а входиться з лайфспану застосунку.
- Тільки LAN: той самий `CORSMiddleware`, а DNS-rebinding Host/Origin-перевірки
  вимкнено з тих самих міркувань, що й `cors_origin_regex` (нестабільний IP
  міні-ПК, довільні пристрої в тій самій мережі). Без власної авторизації —
  та сама модель загроз, що й у REST API поруч.
- Тести — `tests/test_mcp_server.py`, `tests/test_settings_mcp.py`.

### Налаштування (`mcp_config` в `app_settings`, розділ «MCP-сервер» у `SettingsView`)
- `app/services/mcp_config.py` — Pydantic-модель + `load_config`/`save_config`
  (той самий патерн, що й `ai_config`). `TOOLS` — єдине джерело правди: назва →
  притаманний клас (`read`/`write`).
- `_ConfigGatedMCP` (підклас `FastMCP`) читає конфіг **на кожен** `tools/list` і
  `tools/call` — зміни діють без рестарту:
  - `enabled` — вимкнути весь сервер;
  - `tools[name]` — рівень доступу для кожного інструмента: `off` (схований) |
    `read` | `write`. Це бінарний вибір на практиці (read-інструмент може бути
    лише `read`, write-інструмент — лише `write`), тож в UI це **один чекбокс
    на інструмент**: позначено → `read`/`write` за класом, знято → `off`.
- **Дефолт — read-інструменти на `read`, write-інструменти на `off`**: свіжа БД
  без рядка `mcp_config` віддає лише 4 read-інструменти. Старий формат
  (`mode` + `tools: {name: bool}`) підхоплюється: `true`→`read`, `false`→`off`
  (write ніколи не вмикається мовчки).
- API: `GET/PUT /api/settings/mcp` → `{config, tools:[{name,kind,label,access,
  available}], mount_path}`. Ключ `mcp_config` — у `_RESERVED`.

### Інструменти
Read:
- `search_products(query)` — ✅ ціни по мережах з історії (реюз `api/products`).
- `spending_summary(from, to, group_by)` — ✅ `total|store|category|month`
  (реюз `api/dashboard`; гілка `category` = дерево категорій кроку 1).
- `list_receipts(from, to, store?)` — ✅ перелік чеків (тонкі рядки).
- `suggest_store()` — ✅ реюз `services/shopping_list.suggest_stores`.

Write (кожен вмикається окремо чекбоксом):
- `add_to_shopping_list(text, qty?, unit?, note?)` — ✅ делегує в `POST
  /api/shopping-list` (нормалізація + rescan свіжих чеків).
- `add_receipt(total_amount, purchased_at?, shop_name?, items?, …)` — ✅ записує
  покупку в БД під вбудованим акаунтом `scanner` через `_persist_receipt`
  (той самий шлях, що й сканер: дедуп → категоризація → автовідмітка списку).
  У відповіді `items_reconcile` — чи сходяться позиції із сумою чека.
- `add_fuel_purchase(store, fuel="газ", amount? | liters?, price_per_liter?,
  purchased_at?)` — ✅ заправка, **прив'язана до реального акаунта АЗС**
  (`_resolve_store` за назвою/кодом → `_store_account`). Бракуючу величину
  (літри або суму) рахує з `price_per_liter`, інакше з останнього
  `FuelPriceSnapshot` тієї станції (`_latest_fuel_price`, синоніми
  газ/дизель/бензин). Чек — один рядок (назва пального, к-сть у літрах, ціна).
  Приклад: `add_fuel_purchase(store="барс", fuel="газ", amount=1639.53)`.
  Для цього `_persist_receipt` тепер бере `store_code` з `account.store.code`,
  а не хардкодить `"scanner"`.

`suggest_store` / `add_to_shopping_list` лишили захисну перевірку
`_shopping_enabled()` → `{"enabled": false}`, якщо таблиць Кроку 2 немає.

## Рішення (закриті питання)

- **Роутинг чек/документ.** Обидва пороги — форма і кольоровість — у
  `inbox_config` на сторінці налаштувань, підбираємо на тестових сканах.
  Орієнтир форми — ширина чека до ~100 мм. Картки-документи (посвідчення водія,
  ID) не мають потрапляти в чеки — тому й доданий кольоровий маркер (монохром =
  чек, кольорове = документ).
- **Google Drive.** ✅ Реалізовано. Підключення — через UI (кнопка на сторінці
  налаштувань). Scope — `https://www.googleapis.com/auth/drive` (повний: `drive.file`
  не дає бачити наявні папки користувача для вибору «Необроблених»). Client_id/secret
  — поля на сторінці Налаштувань (зашифровано), фолбек `.env` `RS_GOOGLE_CLIENT_*` /
  опції add-on. Refresh-токен — зашифрований
  Fernet у `app_settings.drive_oauth`, назад у API не віддається. До підключення —
  локальне сховище `data/inbox/`. Деталі налаштування — DOCS.md.
- **Каскадний `path` категорій** при перейменуванні батька — так, оновлюємо
  каскадно (вже реалізовано в `api/categories.py`).
- **OCR-рушій — Tesseract `ukr`** (не PaddleOCR).
- **Кабінет ДПС.** Пробуємо структурований чек через `cabinet.tax.gov.ua` як
  пріоритет, далі — по флоу. Вмик/налаштування — у конфізі (`inbox_config` /
  `enable_tax_cabinet`).
- **Файли-шаблони мереж** — додаємо пізніше, лише якщо кабінет ДПС не витягує чек.
  Якщо сервіс покриє 100% — шаблони не потрібні.

## Відкриті питання
