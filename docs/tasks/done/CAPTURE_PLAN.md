# CAPTURE — вільне повідомлення (текст або голос) → чек / список покупок

Узгоджено 2026-09-09. **Статус: кроки 1–4 реалізовані** (2026-09-09);
відкладено лише локальний faster-whisper — розпізнавання голосу поки що хмарне.

Мета: у Telegram-бот (і через MCP) можна написати або
надиктувати звичайну фразу, а застосунок сам вирішує, це чек чи список покупок,
розбирає позиції й записує їх.

Приклади, на яких перевіряємо розбір:

1. «Додай чек парихмахерская Виктория на индустриальной. Стрижка Насти - 600.
   Покраска волос - 1200» → чек, магазин «Парикмахерская Виктория»,
   адреса «Индустриальная», 2 позиції, разом 1800.
2. «Додай чек покупка у бабули возле форы. помидоры 2кг - 160грн.
   огурцы 0,7кг по 50грн» → чек, 2 позиції; «по 50» = ціна за одиницю,
   0.7 × 50 = 35; разом 195.
3. «додай в список покупок яйця 3десятка, морковку, сок, молоко для миланы»
   → 4 позиції списку; «для Мілани» → `note`.
4. «додай в список покупок болты и гайки с шайбами M8 по 20шт, а так же
   крепеж для телевизора» → 4 позиції; спільний модифікатор «M8 по 20шт»
   розкладається на болти/гайки/шайби.
5. «був на барс і заправився газом на 1000грн» → заправка: літри рахуються
   з останньої збереженої ціни станції.
6. «був на барс і залив 15л газа» → заправка: сума рахується з ціни станції.
7. «був на барс і залив на 1000грн газа» → те саме, що (5).

## Архітектура

```
Telegram (текст | voice) ─┐
                          ├→ services/capture.py: parse_capture() → apply
MCP tool capture_text() ──┘        ↑                                   ↓
                            services/ai.py task="intent"   чернетка чека | заправка | список
Telegram voice → services/stt.py (task="stt") → текст ─┘
```

Нові файли: `backend/app/services/capture.py`, `backend/app/services/stt.py`,
`backend/app/services/fuel_entry.py` (пошук станції, ціна, чек на паливо —
винесено з `mcp_server.py`, щоб бот і MCP писали заправку однаково).
Решта — точкові правки в наявних модулях. Нових таблиць і міграцій немає:
використовуються `scan_jobs`, `shopping_list_items`, `app_settings`.

## Крок 1 ✅ — розбір тексту (`services/capture.py`)

`parse_capture(db, text) -> CaptureDraft` — один виклик AI (нова задача
`intent`, маршрут як у `normalize`), строгий JSON:

```json
{"intent":"receipt|fuel|shopping|unknown","confidence":0.0,
 "receipt":{"shop_name":"...","shop_address":"...","purchased_at":null,
            "items":[{"name":"...","qty":1,"unit":"шт|кг|л|десяток",
                      "unit_price":null,"total_price":600}]},
 "fuel":{"store":"барс","fuel":"газ","amount":1000,"liters":null,
          "price_per_liter":null,"purchased_at":null},
 "shopping":[{"text":"...","qty":1,"unit":null,"note":null}]}
```

Правила промпту:

| Кейс | Правило |
|---|---|
| «Стрижка Насти - 600» | `- N` = сума рядка (`total_price`) |
| «огурцы 0,7кг по 50грн» | `по N` = ціна за одиницю → `unit_price` |
| «помидоры 2кг - 160грн» | кількість + одиниця з тексту, `total_price` = 160 |
| «парикмахерская Виктория на индустриальной» | назва → `shop_name`, орієнтир → `shop_address` |
| «покупка у бабули возле форы» | назву не вигадувати, мережу не підставляти |
| «яйца 3десятка» | `qty=3`, `unit="десяток"` |
| «молоко для миланы» | «для …» → `note` |
| «болты и гайки с шайбами M8 по 20шт» | перелік зі спільним модифікатором → окремі позиції |
| «крепеж для телевизора» | «для телевізора» тут частина назви, не `note` |
| «заправився газом на 1000грн» | `amount` = 1000, `liters` порожні |
| «залив 15л газа» | `liters` = 15, `amount` порожня |
| «був на барс» | `store` = «барс», далі шукається серед власних станцій |

Арифметику рахує Python, не модель: `total_price = qty × unit_price` там, де є
лише ціна за одиницю; сума чека = сума рядків; кома як десятковий роздільник;
нормалізація одиниць; низька `confidence` → `intent="unknown"`.

Щоб «у бабули возле форы» не плодило варіантів написання, у промпт додаємо
перелік уже вживаних `shop_name` з чеків акаунта `scanner` як підказку.

- **Список покупок** → пишемо одразу, відповідь «✅ Додано N …» з кнопкою
  «Скасувати» (`cap:undo:<batch_id>`).

  весь розрахунок (`40 л × 25.00 = 1 000.00`, звідки ціна) і кнопка
  «Скасувати» (`cap:undor:<receipt_id>`). Невідома станція або відсутня ціна —
  повідомлення з причиною, нічого не пишеться.
- Прапорець у налаштуваннях Telegram: «розбирати вільний текст через AI».

## Крок 3 ✅ — голос (`services/stt.py`)

- Нова задача `stt` в `ai.py` (`TaskName`, `routing`, метрики й `ai_log` як в `ocr`).
- Два провайдери на вибір (`cloud.stt_provider`, порожньо — голос вимкнено):
  **Google Cloud Speech-to-Text** (`POST /v1/speech:recognize?key=…`, синхронно
  до 60 с, мова `cloud.stt_language` + `cloud.stt_alternative_languages`,
  модель `latest_long`) і **OpenAI-сумісний** `POST /audio/transcriptions`
  (**Groq** — безкоштовний Whisper large-v3, OpenAI сам, або власний
  Whisper-сервер як custom-провайдер). Anthropic такого ендпоінта не має, тому в
  списку його немає. Ключ зберігається окремо під id провайдера — `google_speech`
  має свій. Модель STT прив'язана до провайдера (`STT_MODEL_CHOICES`) і
  автоматично підмінюється при перемиканні, бо чужий id інший провайдер відхиляє.
- Telegram віддає `voice` як OGG/Opus — приймається як є, ffmpeg не потрібен.
  Ліміти 20 МБ / 5 хв з явним повідомленням про перевищення; транскрипт
  цитується у відповіді, бо розпізнавання плутає суми й імена.
- Локальний faster-whisper — опційно, пізніше.
- Settings: модель STT поряд з text/vision + перемикач «розпізнавати голосові».

## Довгий чек — серія фото з перекриттям (2026-09-12, переписано)

**Чинний алгоритм.** Пачка фото — це одна позиція в інбоксі й одне рішення:

1. локально читаємо QR кожного кадру (без моделі);
2. **різні** фіскальні документи → це різні чеки: пачка розпадається на звичайні
   однофотні рядки;
3. **той самий** QR на всіх кадрах → один чек;
4. інакше (QR ніде не прочитався або лише на частині кадрів) → **питаємо**
   користувача двома кнопками «🧩 Один чек» / «🧾 Різні чеки»; до відповіді нічого
   не розпізнається (інакше — виклик моделі на кадр і чеки, які потім прибирати).

Для «одного чека» кадри спершу **склеюються в одне високе зображення**
(`app/scanner/stitch.py`: шов шукається кореляцією нижньої смуги одного кадру у
верхній частині наступного), і далі це звичайне фото — один прохід QR, один OCR,
один виклик моделі. Кадри лишаються на диску (`<job>-p1`, `<job>-p2`, …), рядок
журналу показує їх стрічкою; `POST /api/inbox/scans/{id}/resolve-series?choice=`
відповідає на питання, `GET /api/inbox/scan-input/{id}?part=N` віддає кадр.

Попередній підхід (розпізнавати кожен кадр окремо й зшивати списки позицій)
прибрано разом з `app/scanner/multipart.py`.

## Історія: перша версія серії (2026-09-12)

Чек, довший за кадр, знімають кількома фото, у яких кілька нижніх рядків одного
кадру повторюються вгорі наступного. Кадри склеюються **за розпізнаними
рядками**, не за пікселями: текст на двох кадрах однаковий, а ракурс, світло й
масштаб — ні.

- `app/scanner/multipart.py` — чиста логіка: `overlap_length` шукає найдовший збіг
  «хвіст попереднього = початок наступного» (до 12 рядків, ціни з допуском 0.02),
  `merge_receipts` збирає один чек: шапка з першого кадру, підсумок з останнього,
  що його надрукував, позиції — об'єднання без шва. Розбіжність суми позицій із
  підсумком чека повідомляється окремо: саме так видно, що між кадрами загубився
  рядок.
- `app/services/series_scan.py` — оркестрація: кожен кадр проходить звичайний
  конвеєр (QR на будь-якому кадрі перемагає склеювання — ДПС-документ і є чек),
  далі merge; уся серія — **один** ScanJob, усі кадри лежать поруч на диску
  (`<job>`, `<job>-2`, …), результат завжди чернетка на підтвердження.
  `ai_first=True`: фрагмент без шапки й підсумку шаблонні парсери відкидають.
- API: `POST /api/inbox/upload-series` (кілька файлів у порядку зйомки,
  необов'язковий `scan_job_id` — «додати ще фото» до наявної чернетки).
- Telegram: альбом (кілька фото одним повідомленням) буферизується за
  `media_group_id` і обробляється як серія — одна відповідь на весь альбом; під
  кожною чернеткою кнопка «➕ Додати ще фото цього чека».
- Веб: чекбокс «Кілька фото — це один довгий чек» у формі завантаження та
  кнопка «➕ Ще фото чека» в рядку журналу сканувань.

### Уточнення 2026-09-12

- **QR під печаткою.** Магазин ставить синю печатку прямо на QR; у сірих
  півтонах синє чорніє разом із кодом. Фарба майже невидима у власному каналі,
  тому `scan_qr` після сірих варіантів перебирає канали B/G/R (кожен ще й з
  CLAHE + Otsu та кропом за детектором). Канал, у якому код прочитався,
  потрапляє в нотатки скану: «QR прочитано в синьому каналі».
- **Альбом = одна позиція в журналі.** Раніше кадри альбому ставали окремими
  записами: `handle_update` обробляється по одному, і очікування решти кадрів
  блокувало саме ті апдейти, на які чекало. Тепер кадри буферизуються за
  `media_group_id`, а чекає й обробляє їх фонова задача (`_album_worker`).
- **Два сценарії альбому.** `series_scan.scan_batch` спершу читає QR кожного
  кадру локально (без моделі): якщо кадри називають **різні** фіскальні
  документи — це різні чеки, кожен іде звичайним однофотним шляхом; інакше —
  один чек, кадри склеюються. Явне «➕ Ще фото» до відкритої чернетки ніколи не
  розділяється: користувач уже сказав, що це той самий чек.
- API `/api/inbox/upload-series` тепер повертає `{merged, note, results[]}`.
- **Кнопки під невдалим скануванням.** Фото, з якого нічого не вийшло, раніше
  давало текст без жодної дії. Тепер під ним ті самі кнопки, мінус «Зберегти»:
  «🔄 Пересканувати», «🤖 Розпізнати AI», «➕ Додати ще фото», «🗑 Видалити»,
  посилання на Інбокс (`_review_keyboard(..., save=False)`).
- **Пересканування серії.** Звичайний рескан ганяє `scan_input_path(job)` — для
  серії це лише перший кадр, і чек мовчки коротшав. `series_scan.rescan_series`
  проганяє всі збережені кадри; на цей шлях переведені і бот, і
  `POST /api/inbox/scans/{id}/rescan`.

### Групові дії в журналі сканувань (2026-09-12)

- `POST /api/inbox/scans/bulk` — `{ids, action, with_receipt}`; дії:
  `archive` / `unarchive` / `delete` / `rescan` / `rescan_ai` / `save_draft`.
  Рядки незалежні: кожен повертає власні `ok`/`detail`, один проблемний не
  зупиняє решту. Ліміт 50 рядків за виклик (пересканування коштує виклик моделі
  на рядок). Серія пересканується цілком (`rescan_series`).
- Інбокс: колонка чекбоксів, «вибрати всі показані» (діє саме на видимі рядки,
  не на приховані фільтром), липка панель дій із лічильником. Видалення
  запитує підтвердження і лише після явної згоди забирає збережені чеки.
  Після дії у виборі лишаються тільки рядки, які не вдалися.
