# Сервис сбору чеків — запуск і архітектура

Реверс-інжиніринг API магазинів — у [RESEARCH.md](RESEARCH.md). Тут — про сам сервіс.

## Запуск (без Docker, на цій машині)

**Backend (FastAPI, порт 8001 — 8000 зайнятий іншим процесом на цій машині):**
```bash
cd backend
python3 -m venv venv          # один раз
./venv/bin/pip install -r requirements.txt
./venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8001 --reload
```
БД (SQLite) створюється автоматично в `backend/data/receipts.db` при першому старті,
довідник магазинів (`stores`) наповнюється сам.

> Логін Дніпро-М (телефон+SMS) піднімає headless Chromium і сам проходить
> флоу — потрібні браузери Patchright (`patchright install chromium`). Якщо
> reCAPTCHA сайту почне різати (`"Не вдалося підтвердити…"`) — це адаптивний
> скоринг оточення, відновлюється за години; запасний шлях —
> `scripts/dnipro_m_login.py` (headed-логін руками) або ручний імпорт.

**Frontend (Vue 3 + Vite, порт 5173):**
```bash
cd frontend
nvm use --lts                 # системний node 12 занадто старий для Vite
npm install                   # один раз
npm run dev -- --host 0.0.0.0
```
API-адреса бекенда за замовчуванням **не** задається змінною — `src/lib/api.ts`
бере `window.location.hostname` в момент завантаження сторінки і достукується до
бекенда на тому ж хості, порт 8001. `VITE_API_BASE` в `.env.development` лишений
порожнім навмисно (з коментарем чому) — заповніть його, тільки якщо бекенд
колись переїде на інший хост, ніж фронтенд.

Зараз обидва процеси вже запущені у фоні цієї сесії (backend на 8001, frontend на 5173).

### Доступ з інших пристроїв у локальній мережі
Обидва процеси вже слухають `0.0.0.0`, тож досить відкрити з телефону/іншого
комп'ютера в тій самій Wi-Fi мережі `http://<lan-ip-цієї-машини>:5173`
(IP машини — `hostname -I`, наприклад `192.168.1.50`, але вона не стабільна між
перепідключеннями до Wi-Fi, як зазначено і в RESEARCH.md). Бекендний CORS
(`app/core/config.py::cors_origin_regex`) навмисно дозволяє **будь-який** хост
із приватних діапазонів (`192.168.*`, `10.*`, `172.16-31.*`) і `localhost` на
будь-якому порту — не список конкретних IP, бо IP цієї машини змінюється, а
переналаштовувати CORS вручну щоразу незручно. Публічний інтернет цим regex'ом
не покривається — це свідомо LAN-only сервіс, авторизації в самому UI немає.

```
  adapters/             — по одному файлу на магазин, спільний контракт base.py
    atb.py, fozzy.py, fora.py   — робочі (fetch_receipts реалізовано за задокументованими
                                   в RESEARCH.md ендпоінтами)
    epicentrk.py                 — робочий для offline; online-замовлення падають на 500
                                   з боку сервера Епіцентру (не з нашого) — див. RESEARCH.md
    silpo.py                    — робочий, але інакше: не реверс-інжиніринг застосунку, а
                                   офіційний MCP-сервер Сільпо (OAuth 2.1 + PKCE через
                                   справжній браузерний логін, не SMS-код напряму — див.
                                   AuthType.oauth_browser, api/oauth.py, RESEARCH.md)
    metro.py, scanner.py        — заглушки (документовано, чому не готові)
  services/collector.py — виконує один прохід збору для акаунта, апсертить Receipt/
                          ReceiptItem, пише CollectionRun

                          Receipt — губився мовчки. Виявлено при додаванні Дніпро-М.

  scheduler.py           — раз на хвилину перевіряє Schedule.next_run_at і запускає collector
                          (баг фіксовано 26.08.2026: перше обчислення next_run_at не

                          бо next_run_at щоразу знову бачився як None)
  api/                   — REST: /api/stores, /api/accounts, /api/receipts, /api/dashboard,
                          /api/products (пошук цін по товарах, див. нижче),

frontend/src/
  views/  — Dashboard (+ нараховано/використано бонусів сумарно), Accounts (+ форма
            створення, баланс бонусів у таблиці, кнопка "Код картки" → модалка),
            AccountDetail (токен/розклад/лог запусків, картка магазину —

            (+ нараховано/використано бонусів на чек, кнопка "Редагувати" на чеку

            часткові, лишень надіслані поля змінюються, див.
            AccountUpdate/ReceiptUpdate/ReceiptItemUpdate; + посилання на чек,

            створення чека з нуля — акаунт/дата/товари/фото/посилання, з
            автозбереженням чернетки в localStorage, див. нижче), Products
            (`/products`, пошук цін по товарах з усіх магазинів, див. нижче)
  components/LoyaltyCodeDisplay.vue — рендер картки лояльності (QR/1D-штрихкод/
            PDF417 — останній додано під Укрнафту, її картка "Скануй на АЗК" саме
            такого формату) з перемикачем, спільний для AccountDetail і модалки
            в Accounts. Один рендерер на всі три формати — `bwip-js`, у SVG (не
            canvas: рендер у canvas в цьому браузерному оточенні виходив
            суцільно чорним прямокутником — підтверджено тим самим викликом
            через Node-бекенд бібліотеки, де все гаразд; SVG-шлях цю проблему
            обходить). Одна бібліотека замість двох (`qrcode`+`jsbarcode`
            прибрано з package.json) заразом прибрала й "стрибок" розміру
            картинки при перемиканні формату — раніше кожен формат мав власні
            піксельні розміри canvas, тепер фіксована коробка (квадратна для
            QR, широка для штрихкод/PDF417) і SVG масштабується всередину неї.
  composables/useShopSuggestions.ts — підказки "Магазин"/"Адреса" (`<datalist>`,
            вибір назви автозаповнює адресу) на AddReceipt і формі редагування
            чека, з `GET /api/receipts/shops` — щоб той самий магазин, введений
            вручну, щоразу писався однаково, а не роз'їжджався по написанню
  lib/api.ts — тонка обгортка над fetch під усі ендпоінти бекенда
```

### Модель даних одним реченням
Один **Store** (мережа) → кілька **Account** (окремі "інсталяції", напр. "АТБ Максим" і
"АТБ Насті") → у кожного свій **Credential** (токен) і **Schedule** (розклад) → кожен
запуск лишає **CollectionRun** (лог) і нові рядки **Receipt** з **ReceiptItem**.

### Ручні чеки, посилання, фото (26.08.2026)
Три пов'язані механізми, жоден не йде через `collector.py`/адаптери:

- **`POST /api/receipts`** — ручне створення чека з нуля (`ReceiptCreate`,
  `AddReceiptView.vue`, роут `/receipts/new`): обираєш існуючий **Account** (є
  сенс завести окремий на Store `scanner` — "Сканер (OCR)" — саме для цього;
  такі акаунти одразу `active`, логінитись нема куди), дата, товари вручну.
  `external_id` генерується як `manual:<uuid>` — дедуплікації тут нема, кожен
  ручний чек унікальний за визначенням. `total_price` кожної позиції
  автопідраховується з кількості×ціни (можна перезаписати вручну), сума чека —
  сума позицій.
  **Чернетка**: форма ціла (крім фото — File не серіалізується, і роздувати
  localStorage base64-фото теж не варто) автозберігається в
  `localStorage['receipt-draft-v1']` при кожній зміні (deep watch) і
  відновлюється при заході на `/receipts/new` знову — випадкове закриття
  вкладки/перезавантаження/кнопка "назад" не втрачають уже введене. Чернетка
  чиститься тільки після успішного збереження чека або кнопки "Очистити".
- **`receipt_url`** — просте текстове поле на `Receipt` (не тільки для ручних
  чеків — редагується у ReceiptDetailView для будь-якого чека) для посилання
  типу `vencon.ua/receipt/...` з SMS/email. Просто зберігається й показується
  клікабельним посиланням — вміст сторінки за посиланням не парситься.
- **Фото чека** — `POST/GET/DELETE /api/receipts/{id}/photo`, файл лежить на
  диску в `backend/data/photos/{receipt_id}.<ext>` (лише шлях — `photo_filename`
  — у БД, не сам файл), одне фото на чек (новий аплоад перезаписує старий).
  15 МБ ліміт, `jpg/jpeg/png/webp/heic/heif`. Доступне для будь-якого чека, не
  тільки ручних — задумано як місце під майбутнє OCR-сканування (сфотографував
  → фото прив'язане до чека → колись тут з'явиться розпізнавання позицій).

### Пошук товарів по магазинах (26.08.2026)
`GET /api/products/search?q=...` (`ProductsView.vue`, роут `/products`) — текстовий
пошук по `ReceiptItem.name` (`ILIKE %q%`) серед геть усіх чеків усіх магазинів,
згрупований по (назва товару, магазин). На кожну пару повертає останню ціну (і
коли востаннє купували), мін/макс/середню за весь час та скільки разів куплено.
Групування — в Python, не в SQL (`api/products.py`): вибір "ціни з останнього
чека" на групу — корельований агрегат, який GROUP BY в SQLAlchemy/SQLite чисто
не виражає, а обсяг даних (тисячі рядків) не виправдовує підзапитів заради
цього. Спільного каталогу товарів між мережами нема — кожна мережа називає
товар по-своєму, тож це буквально текстовий пошук по тому, що реально
зустрічалось у чеках, а не довідник з дедуплікацією. Фронтенд групує результат
у картки по назві товару, рядок з найнижчою "останньою ціною" в групі
підсвічується зеленим.

Задумано як перший крок до пошуку оптимального магазину під список покупок —
поки що тільки пошук "хто продає X і почому", сам оптимізатор (сума по кількох
товарах × магазин → який магазин дешевший загалом) ще не зроблено.

### Живий пошук по каталогах магазинів (26.08.2026)
Другий, окремий режим на тій самій сторінці — не з історії чеків, а прямо зараз
запитує **реальний API магазину** (`BaseAdapter.search_catalog(access_token,
extra, query) -> list[CatalogProduct]`, опційний метод, за замовчуванням
`NotImplementedYet`, той самий патерн, що й `get_balance`/`get_fuel_prices`).

`GET /api/products/live-search?q=...` (`api/products.py`) бере по **одному**
активному акаунту на кожен `Store.code` (якщо два акаунти Фори — питається
лише перший-хто-трапився, каталог/ціна не залежать від того, яким саме
акаунтом користуватись), опитує їх усі паралельно (`asyncio.gather`),
best-effort — магазин без підтримки або з помилкою просто мовчки пропускається.

**Реалізовано поки лише для АТБ** (`adapters/atb.py::search_catalog`) — через
стороннього провайдера повнотекстового пошуку `api.multisearch.io`, яким
користується "zakaz" (онлайн-замовлення) частина застосунку АТБ. Токен
акаунта взагалі не потрібен — лише статичні `key`/`id` (публічний віджет-ключ
провайдера) і `location` (id міста в системі multisearch, **не** те саме, що
`cityId` у `zakaz.atbmarket.com` — див. константи в atb.py), усі три
захоплені наживо з реального трафіку застосунку. Підтверджено live-запитом:
цей хост відповідає на звичайний `httpx`-запит без жодної підміни TLS/JA3
відбитка — на відміну від `getReceipts`, тут нема Cloudflare bot-management,
що блокував би чесний клієнт, тож `search_catalog` свідомо використовує
голий `httpx.AsyncClient`, а не спільний `app.core.http.AsyncClient` (curl_cffi
з `impersonate`). Повертає назву, ціну, бренд, картинку, посилання на товар і
булевий прапорець наявності — АТБ-шний ендпоінт `/api/v3/products/group`
(персоналізована ціна з картою лояльності + точний залишок на конкретній
крамниці) свідомо НЕ використано: він вимагає авторизовану сесію з
Cloudflare-виданими `__cf_bm` cookies, а це вже інша історія (див. розділ про
АТБ і Cloudflare нижче) — відтворювати такі cookie без справжнього проходження
челенджу було б обходом антибот-захисту.

**Фора** реалізована теж (`adapters/fora.py::search_catalog`) — на відміну від
АТБ, тут не окремий сторонній хост, а ще один `Method` (`SearchCatalogItems`) на
тому самому RPC-шлюзі `api2.mob.fora.ua`, з тим самим токеном акаунта, що й чеки.
Наявність береться з `calcStoreQuantity > 0` (залишок у конкретній крамниці цього
акаунта); посилання на сторінку товару в відповіді нема — `product_url` лишається
порожнім, на відміну від АТБ. Деталі — RESEARCH.md.

**Fozzy** реалізована теж (`adapters/fozzy.py::search_catalog`) — REST-ендпоінт
на тому самому хості, що й TEComGlobal (`api.tecom.fozzyshop.ua`), тим самим
токеном, наявність береться з `quantity > 0`, посилання на товар — так само
порожнє, як і у Фори. Перевірено акуратно: Fozzy-токен рефрешиться одноразовим
`refresh_token`, який спільний з телефоном (спалити його ручним тестуванням —
розлогінити телефон), тож новий метод перевірено токеном, узятим напряму зі
свіжого перехвату, а не через власний `ensure_fresh_token`/`refresh()` — деталі
в RESEARCH.md.

**Сільпо** реалізована теж (`adapters/silpo.py::search_catalog`) — не перехват
трафіку, а ще один офіційний MCP tool (`silpo_find_products_batch`), як і решта
Сільпо-функціоналу. На відміну від читання історії чеків, тут `branchId`/
`deliveryType`/`timeslot` реально впливають на результат (підставні значення
повертають 0 товарів), тож перед пошуком береться справжній поточний кошик
акаунта (`silpo_get_my_shopping_cart` → `silpo_get_shopping_cart_by_id`).
Наявність — булеве поле `available` прямо у відповіді. Деталі й відомий нюанс
(пошук іноді не знаходить очевидні слова на кшталт "хліб") — RESEARCH.md.

**Епіцентр К** реалізована теж (`adapters/epicentrk.py::search_catalog`) — і
тут був сюрприз: пошук живе на іншому хості (`api.epicentrk.ua`, не
`mobile-api.epicentrk.ua`) з **іншим Bearer-токеном**, який виявився фіксованим
для всього застосунку (не змінюється при виході й повторному вході) — та сама
роль, що й статичний ключ АТБ, просто теж названий "Bearer". Наявність —
`availabilityStatus.code == 100`. Посилання на товар тут є (на відміну від
Фори/Fozzy/Сільпо) — домен відомий напевно. Деталі, включно з нюансом про
"редіректні" відповіді пошуку замість списку товарів — RESEARCH.md.

Усі п'ять мереж (АТБ, Фора, Fozzy, Сільпо, Епіцентр К) тепер відповідають у
живому пошуку разом. METRO/сканер — без live-каталогу, немає що опитувати.

Фронтенд (`ProductsView.vue`) показує обидва режими вкладками: "Живий пошук"
(картки з фото, група по магазину) та "Історія покупок" (таблиця, як було).

### Дніпро-М + гарантія на товари (26.08.2026)

Шоста мережа, перша не через мобільний застосунок — сайт-кабінет
(`dnipro-m.ua`), бо застосунок ігнорує системний проксі Android узагалі
(перехопити нічого не вдалось). Пошук по каталогу (`GET /search/drop-down/`)
працює без жодної авторизації — так само, як multisearch.io в АТБ. Чеки й
баланс технічно реалізовані (`fetch_receipts`/`get_balance`), але сесію не
можна перенести з реального браузера на бекенд — сервер відхиляє будь-яку
відтворену сесію, навіть щойно видану, навіть коли САМ бекенд довершує обмін
SMS-коду. Третя спроба — автоматизувати логін через Playwright (справжній
headless Chromium, за зразком `scripts/silpo_login.py`) — теж провалилась,
але інакше: сайт прямо розпізнав автоматизацію (`"Не вдалося підтвердити,
що запит виконано людиною"`) і відхилив запит; тюнити далі, щоб пройти саме
цю перевірку, означало б обходити антибот-захист, тому скрипт видалено
(усі три спроби — деталі в RESEARCH.md). Тому чеки завантажуються через
"Ручний імпорт" (той самий механізм, що й АТБ):
DevTools браузера → скопіювати тіло `GET /cabinet/order/history/` → вставити
в UI акаунта.

**Гарантія** — новий наскрізний концепт, не специфічний для Дніпро-М:
- `Receipt.has_warranty: bool | None` — чи каже сама мережа, що в цієї покупки
  є гарантійний документ (наразі відповідає лише Дніпро-М, `has_warranty_card`
  у відповіді історії замовлень; для решти мереж завжди `None` — "не звітують").
  Значок 🛡️ біля дати чека в списку `/receipts`; на сторінці чека — картка
  "Гарантія діє до" (якщо дата розпізнана) і повноцінна секція "Гарантійний
  талон" (перегляд/завантаження/заміна/видалення PDF — та сама секція
  доступна для будь-якого чека, не тільки з `has_warranty=true`).
- `BaseAdapter.get_warranty_document(access_token, extra, external_id) -> bytes` —
  опційний метод, повертає сирі байти офіційного документа (у Дніпро-М — PDF),
  проксіюється наживо через `GET /api/receipts/{id}/warranty`. Для Дніпро-М
  зараз не спрацьовує (та сама проблема з сесією, що й у чеків, див. вище) —
  тому додано ручне завантаження: `POST /api/receipts/{id}/warranty`
  (multipart, як фото чека) — файл лягає на диск (`data/warranty/{id}.pdf`,
  `Receipt.warranty_pdf_filename`), і GET спершу віддає саме його, лише потім
  падає на живий адаптерний проксі.
- `Receipt.warranty_expires_at: dt.datetime | None` — парситься автоматично
  з тексту завантаженого PDF (`pypdf`, `api/receipts.py::_extract_warranty_expiry`),
  best-effort за фразою "Гарантія діє з X по Y" (підтверджено на реальному
  талоні Дніпро-М). Не специфічно захардкожено під один магазин технічно —
  просто поки калібровано лише під цю фразу; якщо не збіглось, `has_warranty`
  і сам PDF все одно зберігаються, тільки дата лишається порожньою.
  `has_warranty`/`warranty_expires_at` також можна виставити вручну через
  `PATCH /api/receipts/{id}` — для чеків будь-якої мережі.
- Заразом додано `LoyaltyBalance.discount_percent` / `Account.discount_percent`
  (кешується так само, як `bonus_balance`) — персональний % знижки/кешбеку за
  рівнем лояльності, коли мережа звітує його окремо від суми бонусів (Дніпро-М:
  поле `rate` у `bonuses-info`).

### Про авторизацію (важливо)
Три схеми, залежно від `Store.auth_type`:
- **`phone_otp`** (atb, fozzy, fora) — телефон → SMS-код, повністю автоматизовано через
  `start_login`/`confirm_login` (UI: картка "Вхід по SMS"). Fozzy: `start_login` свідомо
  кидає помилку (reCAPTCHA на SendOtp з боку Fozzy) — там лишається ручний ввід токена
  ("Токен доступу вручну").
- **`oauth_browser`** (silpo) — OAuth 2.1 + PKCE, справжній логін у новій вкладці браузера
  на auth.silpo.ua (UI: картка "Вхід через Сільпо"), бо це не наш реверс-інжиніринг, а
  офіційний MCP-сервер Сільпо — деталі в RESEARCH.md. Той самий логін можна пройти без
  рук з клавіатурою для телефону/кліків, лишивши собі тільки ввід коду з SMS:
  `backend/scripts/silpo_login.py <account-id-або-label>` (Playwright, `pip install -r
  requirements-dev.txt && patchright install chromium` — тільки для цього скрипта,
  не потрібно для роботи самого сервера). За замовчуванням **headless** (жодне вікно
  не зʼявляється, лише термінал питає код із SMS) — перевірено наживо, спрацювало
  з першого разу; саме тому й підходить для майбутнього Docker, де дисплея взагалі
  немає (`patchright install --with-deps chromium` там знадобиться для system-залежностей
  headless-браузера). `SILPO_LOGIN_HEADLESS=0` — показати вікно, лише для дебагу на
  машині з дисплеєм.
- **`device_uuid` / `manual`** (metro, scanner) — заглушки, ще не реалізовано.

Ручний імпорт (`POST /{id}/import`, картка "Ручний імпорт") — окремий шлях для АТБ, де
живий збір заблокований Cloudflare: вставляєте сирий JSON, перехоплений через mitmproxy.
