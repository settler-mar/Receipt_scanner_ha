# Задача: отдельный процесс поиска и объединения дублей чеков

Реализуй в Receipt Scanner отдельный безопасный процесс дедупликации чеков. Не объединяй межканальные чеки непосредственно во время импорта: импорт должен быстро и надёжно сохранять полученные данные, а дедупликация должна запускаться отдельно по расписанию и вручную из админ-интерфейса.

## Цель

Находить одну покупку, пришедшую из разных источников (API магазина, XML/QR ДПС, Telegram, OCR, ручной ввод), и собирать наиболее полную версию чека без потери исходных данных.

## Требования

1. Добавь сущности группы дублей и кандидата на объединение со статусами `pending`, `auto_merged`, `needs_review`, `rejected`, `rolled_back`. Сохраняй оценку совпадения, причины, даты запуска и идентификаторы всех исходных чеков.
2. Поиск кандидатов выполняй отдельным фоновым заданием. Нужны ручной запуск, периодический запуск, защита от параллельных запусков и повторяемость без создания новых одинаковых кандидатов.
3. Сначала сократи выборку по валюте, близкой сумме и временному окну. Затем оцени независимые признаки: внешний ID одного источника, фискальные `fn + id`, RRN, последние 4 цифры карты, ЕДРПОУ/налоговый номер продавца, распознанная сеть, адрес магазина, бонусная карта, состав товаров и объём топлива.
4. Не считай одной покупкой только совпадение суммы и даты. Автоматическое объединение допускай лишь при сильном идентификаторе (например, одинаковый RRN или фискальный ключ) либо при точной сумме, близком времени и ещё одном независимом признаке. Пограничные случаи отправляй на ручную проверку.
5. При объединении выбирай канонический чек. Обычно приоритет: структурированный API магазина, затем структурированный XML ДПС, затем OCR/ручной ввод. При этом выбирай лучшие данные отдельно по полям: наиболее полный список позиций, название и адрес, время, оплата, скидки, ссылка, фото, гарантия, категории и теги.
6. Никогда не удаляй источник без следа. Сохраняй исходные payload, все внешние идентификаторы, происхождение каждого объединённого поля и журнал операции. Переноси ссылки из очереди ДПС и истории сканирования на канонический чек.
7. Объединение должно выполняться в одной транзакции, поддерживать откат и не ломать уникальные ограничения. Категории, пользовательские правки, теги, фото и гарантийные документы нельзя молча перезаписывать.
8. Добавь админ-раздел «Дубли»: список групп, фильтры, причины и оценка совпадения, сравнение чеков рядом, действия «Объединить», «Не дубли», «Откатить», а также кнопку запуска поиска. Показывай прогресс и результат всплывающими уведомлениями.
9. Добавь API для запуска процесса, просмотра кандидатов, подтверждения/отклонения и отката. Ограничь одновременный запуск одним worker lock.
10. Покрой тестами: METRO API + XML ДПС на 7061.43 с разницей времени около трёх минут; повторный запуск; неоднозначные одинаковые суммы; перенос 15 позиций; сохранение тегов/категорий; откат; отсутствие ложного merge для разных магазинов.

## Критерий готовности

Процесс находит существующий METRO-чек и его фискальную копию как одну покупку, показывает понятные причины совпадения, после подтверждения оставляет один полный канонический чек со всеми 15 позициями и ссылками на оба источника, а повторный запуск ничего не дублирует.
